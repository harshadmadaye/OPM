2026-10-05, revision 1 of 2026-10-02 · source: brew-idea run wf_8a106824-7a3 · OPM v0.6.1

Brief: a prioritized list of improvements and new features for OPM, the engineering-workflow plugin for Claude Code. Make it more reliable, easier to adopt and learn, cheaper in tokens and more useful day to day. Say what to fix, what to add next and what to cut.

1Overview

OPM 0.7-0.9: a measured, low-token, test-first Claude Code workflow where status, safety and cost checks run as code instead of model turns, and every release is gated by CI.

Vision: OPM is a low-token, test-first, evidence-before-done workflow plugin for solo and small-team developers using Claude Code in the terminal and VS Code. It pairs measured token costs with guardrails that run on every call, and it uses in-process mods for status and safety at no model cost.

mod marks features built as Claude Code mods: small pieces of plugin code that run inside Claude Code v2.1.287 or later and answer without a Claude turn.

Goals

  • Every release is gated by CI on macOS, Linux and Windows × Node 18/20/22: version/manifest gate, npm pack check, token-budget ceiling, and claude plugin validate --strict / claude plugin test.
  • The token-cost claim is backed by numbers: the linter holds always-on cost in CI, core SKILL.md files drop to about 4KB, and an opt-in local meter records real per-request usage.
  • A new user gets from npx opm-core@latest to a healthy install confirmed by doctor, and small tasks go straight to tdd-workflow instead of the full spec, plan and subagent pipeline.
  • Status, resume and destructive-command safety need no Claude turn and print plain text in the VS Code panel; settings hooks stay the fallback below Claude Code v2.1.287.

Not doing

  • Keeping the story-video alias (removed in 0.7.0)
  • verification-loop as a separate skill (merged into verification-before-completion)
  • push-via-api.sh in the shipped package
  • Static HTML /opm:dashboard or a mod-pane dashboard (/opm:status --all covers it in text)
  • /opm:start skill and bundled sample repo
  • Collapsing the front-door skills into one router, until eval data shows real collisions
  • Panes, bands, status lines or spinner restyles: the VS Code chat panel does not draw them
  • Telemetry or network calls from hooks, mods or the CLI; the meter stays local and off by default
  • Changes to the user's permission mode
  • Moving hot-path hooks to mods unless a spike finds a supported way to stop settings hooks also firing
  • Competitor figures in the README or listings; only OPM's own measured numbers
  • New stacks (Go, Rust, Java)
Success looks like: the 0.8.0 release PR passes CI on all three operating systems with the token-budget check under its ceiling, and in the VS Code chat panel /opm:status prints the open ledger task in about 5 lines without starting a Claude turn.

2Who uses it

Harshad, the author, several projects in VS Code

Wants to know where each project's plan stands and resume without spending tokens or redoing finished tasks, all inside the VS Code chat panel.

  1. Opens a Claude Code session in project A in VS Code.
  2. The SessionStart hook adds one line: open ledger docs/plans/...progress.md, task 4 of 9.
  3. Types /opm:status mod; it prints 5 lines (plan, task, last ruling, done/total) with no Claude turn.
  4. Types /opm:status --all mod to see projects B and C from per-session $.store entries.
  5. Asks Claude to resume; executing-plans reads the ledger and continues at task 4.
  6. Claude tries git push --force origin main; the guard mod holds it with $.ui.ask and he picks cancel.

New adopter, solo TypeScript or Python developer

Wants to install OPM, confirm it works, and get a useful first result without reading the whole README or paying for the full pipeline on a 10-line fix.

  1. Finds OPM in a plugin marketplace listing or the README.
  2. Runs npx opm-core@latest and picks rules in the checkbox picker.
  3. The installer ends with one line: run npx opm-core doctor.
  4. doctor reports Node, hook registration, rule freshness, tools and Claude Code version; one warning says ruff is missing, with the fix.
  5. Asks Claude for a small bug fix; the using-opm routing table sends it straight to tdd-workflow.
  6. The Stop hook skips tsc because no .ts files changed and runs ruff on the edited Python files.

Maintainer cutting a release

Wants to ship fast without breaking manifests, Windows hooks, the always-on token budget or mod contracts when the Claude Code CLI changes.

  1. Opens a PR that adds a new section to executing-plans.
  2. CI runs node:test on the OS × Node matrix, the version/changelog/manifest gate, npm pack --dry-run, validate --strict and plugin test.
  3. The token linter fails: executing-plans is over its soft cap.
  4. Moves the detail into skills/executing-plans/references/ and re-pushes; CI goes green.
  5. Later, the scheduled job against the latest claude CLI fails validate, flagging mod API drift before users hit it.
  6. Fixes it, bumps the declared tested range, and doctor shows the new range.

6Architecture

·npx opm-core CLI: runs outside any session on Node >= 18; installs and stamps rules, doctor checks health and replays synthetic hook payloads, status is the fallback before v2.1.287.
·Shared ledger/status module: parses ledger text into done/total, current task and last ruling, so the CLI, the SessionStart line and /opm:status agree.
·Settings command hooks: SessionStart context plus the resume line, block-no-verify, config-protection, post-edit accumulator, the 90s Stop typecheck and console.log check; the required fallback below v2.1.287.
·OPM mod mod: registers /opm:status and /opm:report, the tool.call destructive guard with $.ui.ask and fail-closed .catch, and the opt-in meter in $.store. Text output only. Takes over hot-path hooks only if the dedupe spike passes.
·Skills, references, agents, rules: using-opm gains the routing table, large skills shrink to about 4KB, brew-idea becomes user-invoked only, stack skills stop duplicating rules.
·GitHub Actions CI: PR gate (node:test matrix, manifest gate, pack dry-run, token linter, validate --strict, plugin test with a pinned claude CLI), a scheduled drift job, a manual or nightly trigger eval.
·explainer-video plugin: keeps the headless browser, ffmpeg and cloud edge-tts out of core, and says that narration text goes to a cloud service.
·Distribution: npm opm-core, GitHub marketplace harshadmadaye/OPM, official and community listings, which go out only after measured numbers and the threat model are published.

8Plan

Scroll sideways for later phases.

1

0.7.0 · Safety net and measurement

Gate every release on deterministic checks and turn the token claim into a CI number. Everything after depends on it.

Features

  • #1GitHub Actions CI
  • #2Remove story-video alias
  • #6Static token-budget linter
  • #24Drop push-via-api.sh from the package

Risks

  • A pinned claude CLI in CI adds a dev-only dependency, and validate output may change.
  • Windows may expose real breakage in dev-server.sh and install-rules.sh, to fix or scope out.
  • bytes/4 is an estimate, so the ceiling needs headroom against flaky failures.

0.7.x · Trim and steady the core

Cut per-run tokens, make routing obvious, make install and hook failures visible. Settings hooks only; works on every Claude Code version.

  • #4Routing table + 30-prompt fixture

  • #23Merge verification-loop
  • #7npx opm-core doctor
  • #8Stop hook fails visibly
  • #13Hook threat model + evasion tests
  • #14brew-idea user-invoked only
  • #15Spin out explainer-video
  • #20Dedupe stack pattern skills

Risks

  • Split skills may lose context the core loop needs; check with the fixture and a manual run.
  • Moving explainer-video breaks existing commands; needs a migration note and a pointer release.
  • The routing table grows using-opm; it must fit within the linter ceiling.
3

0.8.0 · First mod

Add status, safety and measured tokens with no model turns. Text output that works in the VS Code panel; every mod has claude plugin test coverage. Needs v2.1.287+, settings hooks kept as fallback.

Features

  • #10/opm:status + npx fallback + resume line mod
  • #16Destructive-command guard mod
  • #12Opt-in token meter + /opm:report mod
  • #11Tested range + scheduled latest-CLI job

Risks

  • The mod API is new and may change; pin the tested version and let the scheduled job catch drift.
  • Mods are unsandboxed: keep the surface small, no network, publish the validate --json list in the README.
  • $.ui.ask may not render in the VS Code panel or claude -p; the guard must deny with a clear reason there.
  • The 4 MiB $.store is shared by every session; the meter must prune and cap its key.
  • Command output Claude reads still costs a few tokens; keep it to a few lines.
4

0.9.x · Evidence-driven growth

Use measured data to decide merges, migration, positioning and the multi-project view.

Features

  • #17Skill-trigger eval harness
  • #19Hot-path hooks to mod hooks (gated)
  • #5Rewrite README positioning
  • #3Submit to marketplaces

  • claude -p may not trigger skills not checked online, leaving the eval harness with no signal.
  • With no dedupe path, hooks would fire twice, so the migration may be abandoned.
  • Measured cost may be unfavourable, which would change the positioning story.
  • The multi-project view may serve only the author.

10Open questions and assumptions

Challenge these before approving

Open questions

  • When, if ever, should OPM require Claude Code v2.1.287+ and drop the settings-hook fallback?
  • Is explainer-video important enough to stay in core, or is a separate optional plugin acceptable?
  • Should the destructive-command guard be on by default or opt-in, and which other commands should it hold?
  • Does $.ui.ask render in your VS Code chat panel? A quick test decides whether the guard asks or only denies.
  • Do you or others need the multi-project view, now that it would be text rather than a pane or HTML page?
  • Does an opt-in, local-only meter fit how you want "nothing phones home" worded?
  • Which always-on ceiling should CI enforce: the claimed 2,300, or a measured baseline plus headroom?
  • Should the shell helpers support Windows without WSL, or be documented as WSL-only?
  • Should the brew-idea HTML design page stay on by default?

Assumptions

  • Measured locally: skill files total 152,498 bytes, executing-plans 20,151 bytes; .github holds only templates; hooks.json has command hooks only.
  • A mod's 10s hook limit includes awaited $.process.run, so the Stop typecheck stays a 90s settings hook.
  • A plugin's mod cannot stop its own settings hooks also firing, so migrating hooks risks double-firing and needs a spike.
  • $.command.register commands add no always-on description; their output costs only the few tokens Claude reads.
  • The claude CLI runs plugin validate and plugin test in GitHub Actions without sign-in, as the mods docs state.
  • bytes/4 is good enough for a CI ceiling with headroom.
  • $.ui.ask may not render in the VS Code panel or claude -p, so fail-closed deny is the safe default there.
  • edge-tts sends narration text to a Microsoft cloud endpoint, conflicting with core's no-network promise.
  • A marketplace can list a second, optional plugin from the same repo.
  • The on-disk ledger stays the source of truth; $.store holds only a per-session cache plus one capped, opt-in usage key.
  • The skeptic's rebuttal comments stand for its votes; developer feedback counts for no angle.
  • The developer uses the VS Code chat panel, so every mod surface outputs text and never relies on panes, bands or status lines.
  • register.js loads as an ES module without "type": "module"; otherwise a hooks/package.json or .mjs file is needed (spike).
  • claude plugin test runs *.test.ts files without a build step, using the pinned CLI.
  • The shared ledger module is CommonJS imported by the ESM mod; its location is not decided.
  • Store key names (opm.sessions, opm.meter), 14-day pruning and a ~256 KiB meter cap are proposals.
  • The meter toggles with /opm:report --enable and --disable; the verdict only says opt-in.
  • Protected branches are main and master; the exact rm -rf patterns held are not decided.
  • Where $.ui.ask cannot render it throws or reports unsupported, so .catch can deny with a reason.
  • The Stop hook's "nearing the limit" warning fires at about 75s of 90s.
  • The installer writes a version stamp into <repo>/.claude/rules/opm/ for doctor; it does not exist today.
  • doctor exits 0 when all pass, 1 on any fail; warnings exit 0.
  • Starting budget: always-on ceiling ~2,600 tokens (2,300 plus headroom), soft cap ~1,000 tokens (~4KB) per core SKILL.md.

11Why these choices

Four angles plus one revision: product, engineering, skeptic, market, revision 1
  • Product: adoption and visibility first; the cost of a 17th always-on description moved /opm:start's job into doctor plus the routing table.
  • Engineering: reliability and per-run cost first; its Stop-hook cache was deferred because a stale cache could report a false green.
  • Skeptic: stop adding surface and prove the claims; its attacks made positioning and the new guard wait for measured numbers and hardened hooks, and pushed explainer-video out of core.
  • Market: win on credibility against superpowers; its finding that claude -p may not trigger skills not checked online put a spike before the eval harness, and its rules-install hook was cut on consent grounds.
  • Revision 1 (developer feedback): rerun with the Claude Code mods docs; status, the meter, the guard and the multi-project view became mod-based with settings hooks and an npx fallback kept, and the dashboard and panes were cut because nothing draws in the VS Code chat panel.
