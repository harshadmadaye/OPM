opm brew

2026-10-02 · source: brew-idea run wf_8a106824-7a3 · OPM v0.6.1

Brief: a prioritized list of improvements and new features for OPM, the engineering-workflow plugin for Claude Code. Make it more reliable, easier to adopt and learn, cheaper in tokens and more useful day to day. Say what to fix, what to add next and what to cut.

1Overview

OPM 0.7-0.9: a measured, CI-gated plan, TDD and verify plugin with one obvious way in, loud hooks, visible plan progress and fewer always-on tokens, instead of more skills.

Vision: OPM is a lean, measurable plan-TDD-verify workflow plugin for solo and small-team Claude Code developers on TS/React, Python and Flutter. It should prove its token-cost claim, gate every release with CI, and give new users one obvious way in, rather than keep adding skills.

Goals

  • Every release ships from a green test matrix (macOS, Linux, Windows × Node 18/20/22), with a version/changelog/manifest gate and a token ceiling checked before publish.
  • The token-cost claim becomes a published, measured number (always-on and per skill), and per-run cost falls measurably once large skills are split.
  • A new user gets from npx opm-core to a green doctor run and the right skill for their first task in one sitting, guided by a single routing table.
  • Failures and work in progress are visible: hooks never pass silently, the safety guards cover known ways around them, and an open plan shows at session start and in /opm:status.

Not doing

  • Keeping the story-video alias (removed in 0.7.0)
  • Keeping explainer-video in core (moves to an optional package)
  • /opm:start with a bundled sample repo
  • Rewriting five front-door skills into one router
  • A SessionStart hook offering to install rules (rules always need an explicit installer or doctor run)
  • Stop-hook mtime-hash cache
  • Scheduled CI smoke job against the latest Claude Code
  • Multi-repo watching and Notification-driven dashboard features
  • Go/Rust/Java stack-pack template
  • push-via-api.sh shipped through the marketplace
  • engineering-2b-placeholder (empty proposal)
  • Telemetry that leaves the machine (usage log is off by default, local, shared only by copy-paste)
  • New always-on skill descriptions (/opm:status and /opm:dashboard add nothing to the always-on budget)
  • Presenting safety hooks as a security boundary against a malicious actor; they prevent model drift
  • Competitor figures OPM has not measured itself
Success looks like: the 0.8.0 release tag points at a green 9-job CI run. In that same run, the token linter regenerates the why-opm.md table, showing the always-on total under the CI ceiling and executing-plans SKILL.md at about 4KB (down from 20KB).

2Who uses it

New adopter

Solo TS/React, Python or Flutter developer. Wants to install OPM, trust it on their machine and OS, and get the right amount of process for a small first task, without paying for a spec, plan and review.

  1. Reads the README: a measured token table, the tested Claude Code range and OS badges.
  2. Runs npx opm-core, ticks the pre-selected rules, sees one next-step line.
  3. Runs npx opm-core doctor: PASS for plugin and rules, WARN that ruff is not on PATH, with the install command.
  4. Opens Claude Code and asks for a 10-line bug fix.
  5. The routing table calls it a spike and sends it to tdd-workflow (no spec, plan or reviewer).
  6. At Stop, the hook prints "ruff passed in 3s; tsc skipped (no .ts changed)" instead of passing silently.

Returning daily user, mid-plan

Wants to pick up an interrupted plan without re-reading history, and see clearly when a hook blocks or skips something.

  1. Opens a new session. The first line reads "plan 2026-10-01-auth at task 4/9, resume?"
  2. Runs /opm:status: tasks 1-3 done, task 4 in fix round 2/3, the last two rulings.
  3. Says "resume". executing-plans continues from task 4.
  4. The model tries git commit -n. The guard blocks it, names the rule, and suggests fixing the failing hook instead.
  5. At Stop, the hook warns "approaching 90s timeout, dart analyze stopped early" rather than reporting green.

Maintainer (Harshad Madaye)

Wants to ship fast without breaking Windows users or quietly growing the token budget, and wants evidence for what to trim next.

  1. Opens a PR that splits executing-plans into SKILL.md plus references/.
  2. CI runs node:test on 3 OS × 3 Node versions, plus the token budget and release-gate jobs.
  3. The token job reports the always-on total and per-skill change against main, under the ceiling.
  4. Release gate: version, changelog and manifest agree; the npm pack file list holds only bin/, rules/, README and LICENSE.
  5. Before 0.9.0, runs npm run eval:triggers and the manual benchmark, then updates why-opm.md only with numbers that favour or honestly describe OPM.

DoctorCheck

  • id
  • status: PASS, WARN, FAIL
  • message

TokenBudgetReport

  • file path
  • bytes
  • estimated tokens (bytes / chars-per-token constant)
  • always-on (true for descriptions, rules/common, SessionStart output)
  • ceiling
  • delta against main
Generated by the token linter; rendered into the why-opm.md table; checked by the CI token job.

TriggerCase

  • prompt
  • size class: spike, bounded, 8+ tasks, unattended, contested
  • expected skill
30-40 cases in a fixture file; checked against the routing table (statically) and by the manual eval harness.

UsageEvent opt-in

  • timestamp
  • event: skill-invoked, hook-fired, hook-blocked, hook-warned
  • name
  • outcome
  • duration ms
  • project id (salted hash, never a path)
Appended to ~/.opm/usage.jsonl by hooks only when enabled; aggregated by npx opm-core report.

6Architecture

·Plugin content: the workflow itself; using-opm carries the routing table, large skills become about 4KB cores, verification-loop folds into verification-before-completion.
·Hook scripts: SessionStart with the open-plan line; PreToolUse guards; post-edit secret warning; per-language Stop report; optional usage-log append.
·Shared ledger reader: the single parser for progress.md and STATE.md, so the SessionStart line, /opm:status and /opm:dashboard cannot drift apart.
·/opm:status and /opm:dashboard: status prints the ledger summary; dashboard writes one static HTML file, no network, no live watching.
·opm-core CLI: installer writes rules and the RulesStamp; doctor runs checks and replays hook scripts with synthetic payloads; report summarises the opt-in usage log.
·Token budget linter: runs on the maintainer machine and in CI; measures always-on and per-skill bytes, enforces the ceiling, regenerates the why-opm.md table.
·GitHub Actions: node:test matrix, token job, release-gate job (versions agree, npm pack --dry-run, no tracked debug logs or stray config).
·Trigger evals and benchmark: maintainer machine only, kept out of npm test; static description-overlap check until the spike works.

Node >=18, CommonJS, zero runtime dependencies (unchanged)Installer, hooks, doctor and linter install anywhere through npx; keeps the "nothing to audit, nothing phones home" promise.

GitHub Actions matrix (ubuntu, macos, windows × Node 18/20/22)The repo is already on GitHub and Windows hook behaviour is unverified; the cheapest way to cover all three OSes.
Bytes-per-token estimate with a named constantNo tokenizer dependency; the method is published next to the numbers so the claim stays honest.
Markdown SKILL.md cores plus references/*.mdCuts per-run tokens with no new tooling; milestone-planning already ships a templates/ sibling folder.
Plain-text ledger and STATE files as the only sourceThe data already exists on disk and survives compaction; no new store needed.
JSON Lines at ~/.opm/usage.jsonl, off by defaultAppend-only and dependency-free; easy to aggregate, inspect or delete; stays local.
Static single-file HTML for /opm:dashboardNo server, framework or network; matches the read-only scope; opens in any browser.

8Plan

Scroll sideways for later phases. Version numbers are illustrative groupings, not commitments.

1

0.7.0 · Gate and measure

Every release is tested on all three OSes, and the token-cost claim becomes a number enforced in CI. Everything after depends on this.

Features

  • #1GitHub Actions CI
  • #3Token budget linter
  • #2Remove story-video alias
  • #10Repo hygiene

Risks

  • Windows CI may expose broken shell helpers (dev-server.sh, install-rules.sh) and widen the phase.
  • Measured always-on cost may exceed 2,300 tokens, forcing a README correction first.
  • Removing story-video breaks alias users; needs a clear changelog note.
2

0.8.0 · Reliability and the front door

The install can be diagnosed, hooks fail loudly and honestly, users reach the right skill, and per-run tokens fall measurably.

Features

  • #6npx opm-core doctor
  • #7Stop hook degrades visibly
  • #12Harden existing safety hooks
  • #4Routing table in using-opm
  • #8Split large skills
  • #17Merge verification-loop
  • #9/opm:status + SessionStart line

Risks

  • The routing table adds always-on tokens; must stay under the ceiling.
  • Split skills may change behaviour if the model skips reference files; without evals only caught by hand.
  • Synthetic hook payloads may not match real ones, giving doctor false confidence.
3

0.9.0 · Trim scope and earn credibility

Shrink the core to the engineering loop, back the claims with evidence, then position and distribute OPM.

Features

  • #23explainer-video out of core
  • #13brew-idea explicit only
  • #18Deduplicate stack guidance
  • #19Skill-trigger eval harness
  • #15Same-task token benchmark
  • #5Sharpen positioning
  • #11Destructive-command guard + secret check
  • #14Submit to marketplaces

Risks

  • The claude -p skill-triggering limitation not checked online may make automated evals impossible, leaving a static overlap check.
  • Benchmark results may be noisy or unfavourable; positioning must follow them.
  • A separate explainer-video package splits maintenance, and the author may depend on it.
4

Later, evidence-gated · Usage evidence and power-user views

Collect local, opt-in evidence on which skills get used; build the dashboard only if other users show they need it.

Features

  • #16Opt-in local usage log + report
  • #20Static read-only /opm:dashboard

Risks

  • Hook writes to ~/.opm add Windows path/permission failures and latency on every hook call.
  • Few users may opt in, so evidence stays thin.
  • The dashboard may serve only the author; stop if two or three users do not confirm the need.

10Open questions and assumptions

Challenge these before approving

Open questions

  • Does anyone besides you run several OPM projects at once? That decides whether the dashboard is built.
  • Is explainer-video important to your workflow, and would you accept moving it to an optional package (for example opm-extras)?
  • What always-on token ceiling should CI enforce: the claimed 2,300, or today's measured value plus a margin?
  • Is native Windows (no WSL) supported, or are the shell helpers macOS/Linux/WSL only?
  • Which Claude Code versions have you actually tested, so the README can state a range?
  • Should brew-idea's HTML page stay a default for your own use, or become opt-in?
  • What is the stray Firebase config in the repo root for, and can it go?
  • Does push-via-api.sh exist because of the personal-account constraint, and can it move out of the repo?
  • Will you spend tokens on a nightly or manual trigger-eval run, and roughly how much per run?
  • Do you want OPM in the official Anthropic plugin marketplace, and will you meet its requirements?

Assumptions

  • Every installed skill's description counts toward always-on cost, so removing or merging a skill lowers it.
  • Bytes ÷ about 4 is accurate enough for a CI ceiling; the constant is published as an estimate.
  • Plugin skills can load sibling references/ files on demand (engineering's claim, not verified).
  • Superpowers' star count and marketplace placement, and the report that claude -p does not trigger skills not checked online
  • Release numbers are illustrative groupings; no stated deadline or budget.
  • Ranking is impact ÷ effort, ties broken by angles in favour; keep and cut entries listed after work items.
  • Verified directly: no .github/workflows exists; SKILL.md files total about 152KB (executing-plans 20KB); npm ships only bin/, rules/, README and LICENSE. Hook, installer and skill body quality were not read.
  • An angle that authored an idea counts as a vote for it.
  • /opm:status and /opm:dashboard are slash commands, not skills, and command descriptions do not count toward the always-on budget (to verify).
  • The installer writes a new .claude/rules/opm/.opm-version stamp with per-file hashes; no existing stamp is described.
  • doctor finds the installed plugin directory to replay hooks, so the npm package need not include hooks/.
  • The tested Claude Code range lives in package.json or README; how doctor reads the local version (for example claude --version) is assumed.
  • The ~4KB SKILL.md target and the CI ceiling are set from the first linter run.
  • Always-on cost = skill and agent descriptions + rules/common + SessionStart output; the linter documents what it counts.
  • A ledger is open if its plan has a task with no "complete" line; stale ledgers are shown with their date, not hidden.
  • The dashboard reads the current repo plus paths in an optional local config (for example ~/.opm/projects.json); no discovery or watching.
  • Usage events store a salted project hash, never a path or prompt text; report output holds only counts.
  • The secret check on edit warns, does not block, using a small built-in pattern list.
  • The rm -rf guard blocks only paths outside the repo or root-like targets; exact rules decided while building.
  • The fixture holds 30 cases; the eval harness grows it to 30-40 once the claude -p spike shows whether skills trigger.
  • Hook messages reach the transcript through existing hook output channels; rendering depends on Claude Code.
  • Phases map to 0.7.0, 0.8.0 and 0.9.0; Phase 4 has no version until it has evidence.
  • All four angles returned proposals and every angle was rebutted.

11Why these choices

Four angles argued this out: product, engineering, skeptic, market
  • Product: adoption and visibility first; the cost of a 17th always-on description moved /opm:start's job into doctor plus the routing table.
  • Engineering: reliability and per-run cost first; its Stop-hook cache was deferred because a stale cache could report a false green.
  • Skeptic: stop adding surface and prove the claims; its attacks made positioning and the new guard wait for measured numbers and hardened hooks, and pushed explainer-video out of core.
  • Market: win on credibility against superpowers; its finding that claude -p may not trigger skills not checked online put a spike before the eval harness, and its first-run rules-install hook was cut on consent grounds.
