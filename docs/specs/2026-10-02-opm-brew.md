# opm brew

Date: 2026-10-02
Brief: Give a prioritized improvements list and new feature updates for this current plugin project: OPM, an opinionated engineering-workflow plugin for Claude Code (v0.6.1) used by developers in the terminal and IDE. It ships skills, reviewer agents, safety hooks, rules and an npx installer. Improve reliability, adoption, onboarding, token cost and day-to-day developer usefulness; propose what to fix, what to add next, and what to cut.
Source: brew-idea run wf_8a106824-7a3

## Vision

OPM is a lean, measurable plan-TDD-verify workflow plugin for solo and small-team Claude Code developers on TS/React, Python and Flutter. It should prove its token-cost claim, gate every release with CI, and give new users one obvious way in, rather than keep adding skills.

OPM 0.7-0.9: a measured, CI-gated plan, TDD and verify plugin with one obvious way in, loud hooks, visible plan progress and fewer always-on tokens, instead of more skills.

Goals:
- Every release is published from a green test matrix (macOS, Linux and Windows, each on Node 18/20/22), with a version/changelog/manifest gate and a token ceiling enforced before publish.
- The token-cost claim becomes a published, measured number (always-on and per skill). Per-run cost then falls measurably after large skills are split into a core SKILL.md plus on-demand references.
- A new user can go from `npx opm-core` to a green `doctor` run and the right skill for their first task in one sitting, guided by a single routing table.
- Failures and in-flight work are visible: hooks never pass silently, safety guards cover known evasions, and an open plan ledger is shown at session start and through /opm:status.

Not doing:
- Keeping the story-video alias skill (it is removed in 0.7.0)
- Keeping explainer-video in the core plugin (it moves to an optional package)
- /opm:start skill with a bundled sample repo (cut)
- Rewrite of five front-door skills into a single router (cut)
- SessionStart hook offering to install rules on first run (cut). Installing rules always needs an explicit installer or doctor run.
- Stop-hook mtime-hash cache subsystem (cut)
- Scheduled CI smoke job against the latest Claude Code (cut)
- Multi-repo watching and Notification-driven dashboard features (cut)
- Go/Rust/Java stack-pack template and contribution guide (cut)
- push-via-api.sh in the repo shipped through the marketplace (cut)
- engineering-2b-placeholder (empty proposal) (cut)
- No telemetry that leaves the machine. The usage log is off by default, stays local, and is shared only by copy-paste.
- No new always-on skill descriptions. /opm:status and /opm:dashboard must not add to the always-on budget.
- Safety hooks are not presented as a security boundary against a malicious actor. They prevent model drift.
- No competitor figures that OPM has not measured itself.

Success looks like: The 0.8.0 release tag points at a green 9-job CI run. In that same run, the token linter regenerates the why-opm.md table, which shows the always-on total under the CI ceiling and executing-plans SKILL.md at about 4KB (down from 20KB).

## Design

### Who uses it

**New adopter (solo TS/React, Python or Flutter developer)**: Install OPM, trust that it works on their machine and OS, and get routed to the right amount of process for a small first task without paying for spec, plan and review.
Flow: Reads the README: a measured token table, the tested Claude Code range and OS badges → Runs `npx opm-core`, ticks the pre-selected rule set, and sees one next-step line → Runs `npx opm-core doctor`: PASS for plugin and rules, WARN that ruff is not on PATH, with the install command → Opens Claude Code and asks for a 10-line bug fix → The using-opm routing table classifies it as a spike and sends it to tdd-workflow (no spec, plan or reviewer) → At Stop, the hook prints 'ruff passed in 3s; tsc skipped (no .ts changed)' instead of passing silently

**Returning daily user mid-plan**: Pick up an interrupted multi-task plan without re-reading history, and get clear signals when a hook blocks or skips something.
Flow: Opens a new session. The SessionStart line reads 'plan 2026-10-01-auth at task 4/9, resume?' → Runs /opm:status: tasks 1-3 complete, task 4 in fix round 2/3, the last two rulings → Says 'resume'. executing-plans continues from the ledger at task 4 → The model tries `git commit -n`. The guard blocks it, names the rule, and suggests fixing the failing hook instead → At Stop, the hook warns 'approaching 90s timeout, dart analyze stopped early' rather than reporting green

**Maintainer (Harshad Madaye)**: Ship releases quickly without breaking Windows users or quietly inflating the token budget, and get evidence for what to trim next.
Flow: Opens a PR that splits executing-plans into SKILL.md plus references/ → CI runs node:test on 3 OS x 3 Node versions, plus the token budget and release-gate jobs → The token job reports the always-on total and per-skill delta against main, under the ceiling → Release gate: version, changelog and manifest agree, and the npm pack --dry-run file list contains only bin/, rules/, README and LICENSE → Before 0.9.0, runs `npm run eval:triggers` and the manual benchmark locally, then updates why-opm.md only with numbers that favour or honestly describe OPM

### Screens

One block per surface, in the order a user meets them.

#### README, why-opm.md and marketplace listing (page)

Position OPM against alternatives using only numbers OPM measured itself, and give one install path. Delivers: Sharpen README and why-opm.md positioning against superpowers, led by measured cost numbers; Submit to the official and community plugin marketplaces once CI and token numbers exist; GitHub Actions CI: node:test on macOS/Linux/Windows x Node 18/20/22, plus a pre-publish version/changelog/manifest gate and npm pack --dry-run; Token budget linter: zero-dependency script reporting always-on and per-skill tokens, with a CI ceiling and a table in why-opm.md.

```
hero: one-line pitch and the `npx opm-core@latest` command
cost table: always-on and per-skill tokens generated by the linter, with a method note (bytes-per-token estimate)
which skill when: the routing table, copied from using-opm
compatibility: tested Node versions, tested Claude Code range, OS badges from CI
safety: hook list, with the threat model stated as drift prevention
footer: changelog link and troubleshooting ('run doctor')
```

States: Empty: the comparison section is not published until linter (and optionally benchmark) numbers exist. Error: if the numbers are unfavourable, the comparison section is dropped and the measured table stays.

#### npx opm-core (installer) (command)

Install the plugin and copy per-repo rules, then point the user to exactly one next step. Delivers: Five reviewer agents and the per-repo rules installer with its checkbox picker; npx opm-core doctor: plugin registration, rules present and current, Node version, tool presence (tsc/ruff/dart), hooks replayed against synthetic payloads, Claude Code version against the tested range, and the installer ending with one next-step line.

```
banner: opm-core version and target repo path
checkbox list: rule sets (common, typescript, react, python, dart), with the detected stack pre-ticked
progress: one line per step (plugin install, rules copy, version stamp written)
summary: files written under .claude/rules/opm/
footer: one next-step line, 'Run npx opm-core doctor, then ask Claude Code for your first task'
```

States: Empty: no git repo detected, so it installs the plugin only and says so. Loading: one line per step. Error: names the failed step and the fix command, exits non-zero, no stack trace.

#### npx opm-core doctor / report (command)

Diagnose an install in one run (doctor), and optionally print an anonymised local usage summary (report). Delivers: npx opm-core doctor: plugin registration, rules present and current, Node version, tool presence (tsc/ruff/dart), hooks replayed against synthetic payloads, Claude Code version against the tested range, and the installer ending with one next-step line; Opt-in, local-only usage log (~/.opm/usage.jsonl, off by default) plus `npx opm-core report` for an anonymised copy-paste summary.

```
header: OPM plugin version, Node version, Claude Code version against the tested range
checklist: one PASS/WARN/FAIL row per check (plugin registered, rules present, rules stamp matches plugin version, tsc/ruff/dart for detected stacks, each hook replayed on a synthetic payload)
fix hints: one copy-paste command under each non-pass row
footer: pass/warn/fail counts, with exit code 1 on any FAIL
report mode: logging status (off by default, with how to enable), skill and hook counts for the window, then an anonymised block to paste into an issue
```

States: Empty: report with logging off prints how to opt in and exits 0. Loading: checks stream line by line. Error: a check that crashes shows FAIL with its reason and the rest still run.

#### Skill front door (using-opm routing and on-demand skills) (other)

Route each request to the right-sized workflow, and load only the core of a skill unless more is needed. Delivers: Routing table in using-opm (size ladder: spike to tdd-workflow, bounded to brainstorming then writing-plans, 8+ tasks to milestone-planning, unattended to jump-start, contested to brew-idea) plus a 30-prompt trigger fixture; Split large skills into a short SKILL.md (about 4KB) plus references/ files loaded on demand, starting with executing-plans (20KB) and the stack-pattern skills (12-14KB); Merge verification-loop into verification-before-completion (quick gate in SKILL.md, full loop in a reference file); Deduplicate stack guidance between rules and the react/python/flutter pattern skills; brew-idea: explicit invocation only, with the HTML design page opt-in; Core loop skills (brainstorming, writing-plans, executing-plans ledger, tdd-workflow, compound-learnings, milestone-planning, jump-start).

```
routing table in using-opm: size class, signal and target skill, one row each (spike, bounded, 8+ tasks, unattended, contested)
SKILL.md core: about 4KB of steps, each pointer phrased 'read references/<x>.md when <condition>'
references/: detailed guidance and templates, loaded only when a pointer fires
verification-before-completion: quick gate inline, full build/types/lint/tests/secrets loop in references/full-loop.md
brew-idea: runs only when named; the HTML page is generated only on request
```

States: Error: if the model skips a reference file, the SKILL.md core still gives a safe minimal path. Mis-triggering shows up in the 30-prompt fixture. Empty: a request that matches no row falls back to asking about size in one question.

#### In-session hook messages (other)

Make every hook outcome visible in the Claude Code transcript: blocks, skips, warnings and open plans. Delivers: Stop hook degrades visibly: skip when no files of that language changed, warn on a missing tool or an approaching 90s timeout, never pass silently; Harden existing safety hooks against cheap evasions (git commit -n, HUSKY=0) with tests, and document the threat model as drift prevention; Destructive-command guard hook (rm -rf, force-push to main, git reset --hard) and secret-leak detection on edit; /opm:status plus a SessionStart one-liner when a ledger is open ('plan X at task 4/9, resume?'); Opt-in, local-only usage log (~/.opm/usage.jsonl, off by default) plus `npx opm-core report` for an anonymised copy-paste summary.

```
SessionStart: existing context injection, plus one line 'plan <name> at task N/M, resume?' when a ledger is open
PreToolUse block: what was blocked, the rule, and a safe alternative (for example, fix the hook rather than using commit -n)
post-edit warning: possible secret in <file>:<line>, with the value masked
Stop summary: one line per language ('ruff passed 3s', 'tsc skipped: no .ts changed', 'dart not found: install or ignore', 'timeout near: stopped early')
```

States: Empty: no open ledger means no SessionStart line. Error: a hook that crashes prints a one-line reason and does not block work. A missing tool is a WARN, never a silent PASS.

#### /opm:status (command)

Show where the current plan or milestone stands, from the on-disk ledger, without reading history. Delivers: /opm:status plus a SessionStart one-liner when a ledger is open ('plan X at task 4/9, resume?').

```
header: repo name and active plan file (or milestone from STATE.md)
progress: task N/M, each task marked complete, fix round R/3 or pending
rulings: the latest 3 'Ruling:' lines from the ledger
deferred: count of deferred minors
next action: 'resume with executing-plans' or 'no open plan'
```

States: Empty: no ledger in docs/plans/, so it says there is no open plan and how to start one. Loading: instant, a local file read. Error: a malformed ledger shows the file path and the line that failed to parse.

#### /opm:dashboard (page)

A static, read-only HTML overview of plan and milestone progress for users who run several OPM projects. Built only after /opm:status ships and is validated with other users. Delivers: Static, read-only /opm:dashboard built from ledger and STATE files on top of /opm:status.

```
header: generated-at time and the list of project paths read
table: one row per project (active plan, tasks done/total, last ledger update, milestone phase)
detail: per project, the latest rulings and deferred minors
footer: the command to regenerate, with no live refresh
```

States: Empty: no projects with ledgers shows how to add paths. Error: an unreadable project is listed with its reason and the others still render. Loading: generated once and written to a local file.

#### Release gate (GitHub Actions and maintainer scripts) (other)

Block any PR or publish that breaks tests on an OS, exceeds the token ceiling, or ships inconsistent versions or stray files, and hold the manual evidence runs. Delivers: GitHub Actions CI: node:test on macOS/Linux/Windows x Node 18/20/22, plus a pre-publish version/changelog/manifest gate and npm pack --dry-run; Token budget linter: zero-dependency script reporting always-on and per-skill tokens, with a CI ceiling and a table in why-opm.md; Repo hygiene: explain or delete the stray Firebase config, keep firebase-debug.log out, and confirm the package contents in CI; Skill-trigger eval harness (30-40 prompts with the expected skill), nightly or manual, after a design spike; Reproducible same-task token benchmark (OPM vs bare Claude Code), run manually.

```
PR checks: 9 test jobs (3 OS x Node 18/20/22)
token job: always-on total against the ceiling, the 5 largest skills, delta against main
release-gate job: package.json, plugin.json, marketplace.json and CHANGELOG versions agree; npm pack --dry-run file list; no tracked *.log or unexplained Firebase config
local scripts: `npm run tokens`, `npm run eval:triggers` (manual, spends tokens), benchmark steps in docs/benchmarks/
```

States: Error: a failing job names the file and how far it exceeds the ceiling or which versions disagree. Empty: until the eval spike succeeds, eval:triggers runs only the static description-overlap check. Loading: standard Actions progress.

### Architecture

| Part | Runs on | Role |
|---|---|---|
| Plugin content: skills (SKILL.md plus new references/) and 5 agents | Inside the user's Claude Code session, loaded by the model on demand from the plugin directory | The workflow itself. using-opm carries the routing table. Large skills are split into about 4KB cores. verification-loop is folded into verification-before-completion. |
| Hook scripts (hooks/scripts/*.js, existing plus a destructive-command guard and a secret check) | Claude Code hook runner: one Node process per hook call on the user's machine (macOS, Linux, Windows) | SessionStart injection plus the open-ledger line; PreToolUse guards (no-verify variants, HUSKY=0, rm -rf, force-push to main, reset --hard); post-edit secret warning; a Stop hook that reports per language; an optional append to the usage log when enabled. |
| Shared ledger reader (new hooks/lib/ledger.js) | In the plugin, required by hooks and commands; pure Node with no dependencies | The single parser for progress.md and STATE.md, returning plan, task N/M, fix rounds and rulings. Used by the SessionStart line, /opm:status and /opm:dashboard, so their output cannot drift apart. |
| /opm:status and /opm:dashboard commands (new) | Claude Code slash commands that call Node scripts in the plugin on the user's machine | status prints the ledger summary. dashboard writes one static, read-only HTML file from the ledgers and STATE files of the listed project paths, with no network or live watching. |
| opm-core CLI (bin/install.js plus new bin/doctor.js and bin/report.js) | The user's terminal through npx; shipped in the npm package | The installer writes rules and the new RulesStamp and prints a single next-step line. doctor runs checks and replays installed hook scripts with synthetic payloads. report aggregates the opt-in usage log into an anonymised summary. |
| Token budget linter (new scripts/token-budget.js) | Maintainer machine and CI | Measures always-on bytes (skill descriptions, rules/common, SessionStart output) and per-skill bytes, converts them to estimated tokens with a named constant, enforces the ceiling, and regenerates the why-opm.md table. |
| GitHub Actions workflows (new .github/workflows/) | GitHub-hosted runners | node:test across 3 OS x Node 18/20/22, the token job, and a release-gate job (version/changelog/manifest consistency, npm pack --dry-run, no tracked debug logs or stray config). |
| Trigger eval harness and token benchmark (new scripts/evals/, docs/benchmarks/) | Maintainer machine only, manual, spends tokens; kept out of `npm test` | Runs the TriggerCase fixture against real skill triggering (after a spike, falling back to a static description-overlap check) and the same-task comparison of OPM against bare Claude Code. |

### Stack

| Choice | Reason |
|---|---|
| Node >=18, CommonJS, zero runtime dependencies (unchanged) | This keeps the installer, hooks, doctor and linter installable everywhere through npx and keeps the 'nothing to audit, nothing phones home' promise. |
| node:test for all automated tests, including the new doctor, guards, ledger reader and linter | It is already used by the 15 test files and needs no network, browser or ffmpeg, so CI stays fast and free. |
| GitHub Actions matrix (ubuntu, macos, windows x Node 18/20/22) | The repo is already on GitHub and Windows hook behaviour is unverified; a matrix is the cheapest way to cover all three OSes. |
| Bytes-per-token estimate with a named constant instead of a tokenizer | It adds no dependency. The method is stated next to the published numbers, so the claim stays honest. |
| Markdown SKILL.md cores plus references/*.md siblings | This cuts per-run tokens without new tooling. milestone-planning already ships a templates/ sibling directory, so the plugin layout supports extra files. |
| Plain-text ledger and STATE files as the only source for status and dashboard | The data already exists on disk and survives compaction. No new store is needed. |
| JSON Lines at ~/.opm/usage.jsonl, off by default | Append-only and dependency-free, it is easy for `report` to aggregate and for a user to inspect or delete. It stays local. |
| Static single-file HTML for /opm:dashboard, with no external requests | It needs no server, framework or network, matches the read-only scope, and opens in any browser. |

## Plan

### Phase 1: (0.7.0): Gate and measure

Goal: Every release is tested on all three OSes, and the token-cost claim becomes a number enforced in CI. Everything after this phase depends on these numbers and this gate.

Features:
- GitHub Actions CI: node:test on macOS/Linux/Windows x Node 18/20/22, plus a pre-publish version/changelog/manifest gate and npm pack --dry-run
- Token budget linter: zero-dependency script reporting always-on and per-skill tokens, with a CI ceiling and a table in why-opm.md
- Remove the story-video alias skill in 0.7.0
- Repo hygiene: explain or delete the stray Firebase config, keep firebase-debug.log out, and confirm the package contents in CI

Risks:
- The Windows CI run may expose broken shell helpers (dev-server.sh, install-rules.sh) and widen the phase
- The measured always-on cost may exceed 2,300 tokens, forcing a README correction before any marketing
- Removing story-video breaks existing users of the alias, so it needs a clear changelog note

### Phase 2: (0.8.0): Reliability and the front door

Goal: The install can be diagnosed, the hooks fail loudly and honestly, users are routed to the right skill, and per-run tokens fall measurably.

Features:
- npx opm-core doctor: plugin registration, rules present and current, Node version, tool presence (tsc/ruff/dart), hooks replayed against synthetic payloads, Claude Code version against the tested range, and the installer ending with one next-step line
- Stop hook degrades visibly: skip when no files of that language changed, warn on a missing tool or an approaching 90s timeout, never pass silently
- Harden existing safety hooks against cheap evasions (git commit -n, HUSKY=0) with tests, and document the threat model as drift prevention
- Routing table in using-opm (size ladder: spike to tdd-workflow, bounded to brainstorming then writing-plans, 8+ tasks to milestone-planning, unattended to jump-start, contested to brew-idea) plus a 30-prompt trigger fixture
- Split large skills into a short SKILL.md (about 4KB) plus references/ files loaded on demand, starting with executing-plans (20KB) and the stack-pattern skills (12-14KB)
- Merge verification-loop into verification-before-completion (quick gate in SKILL.md, full loop in a reference file)
- /opm:status plus a SessionStart one-liner when a ledger is open ('plan X at task 4/9, resume?')

Risks:
- The routing table adds always-on tokens to using-opm, so it must stay under the linter ceiling
- Splitting skills may change model behaviour if the model does not read the reference files when it should, and without evals this is detected only by hand
- Synthetic hook payloads may not match real Claude Code payloads, which would give doctor false confidence

### Phase 3: (0.9.0): Trim scope and earn credibility

Goal: Shrink the core to the engineering loop, back the claims with evidence, then position and distribute OPM.

Features:
- explainer-video in the core plugin
- brew-idea: explicit invocation only, with the HTML design page opt-in
- Deduplicate stack guidance between rules and the react/python/flutter pattern skills
- Skill-trigger eval harness (30-40 prompts with the expected skill), nightly or manual, after a design spike
- Reproducible same-task token benchmark (OPM vs bare Claude Code), run manually
- Sharpen README and why-opm.md positioning against superpowers, led by measured cost numbers
- Destructive-command guard hook (rm -rf, force-push to main, git reset --hard) and secret-leak detection on edit
- Submit to the official and community plugin marketplaces once CI and token numbers exist

Risks:
- The `claude -p` skill-triggering limitation (unverified) may make automated evals impossible, leaving only a static overlap check
- Benchmark results may be noisy or unfavourable to OPM, and positioning must follow them
- Extracting explainer-video into a separate package splits maintenance across two packages, and the author may depend on it

### Phase 4: (later, evidence-gated): Usage evidence and power-user views

Goal: Collect local, opt-in evidence on which skills are used, and build the dashboard only if other users show they need it.

Features:
- Opt-in, local-only usage log (~/.opm/usage.jsonl, off by default) plus `npx opm-core report` for an anonymised copy-paste summary
- Static, read-only /opm:dashboard built from ledger and STATE files on top of /opm:status

Risks:
- Hook writes to ~/.opm add Windows path and permission failure modes and latency on every hook call
- Few users may opt in, so the evidence stays thin
- The dashboard may serve only the author, so stop if validation with two or three users fails

## Assumptions

- Skill descriptions for every installed skill count toward the always-on token cost, so removing or merging a skill lowers it.
- A bytes-divided-by-about-4 token estimate is accurate enough for a CI budget ceiling, with no tokenizer dependency.
- Plugin skills can load sibling references/ files on demand (engineering's claim, not verified here).
- Competitor facts (superpowers' star count and official-marketplace placement) and the report that `claude -p` does not trigger skills are unverified secondary-source claims.
- Release numbers (0.7.0, 0.8.0, 0.9.0) are illustrative groupings, not commitments; there is no stated deadline or budget.
- Ranking within the feature list is impact divided by effort for work items, ties broken by the number of angles in favour; keep and cut entries are listed after the ranked work items, not interleaved.
- I verified only these facts directly: no .github/workflows exists, SKILL.md files total about 152KB with executing-plans at 20KB, and the npm files list ships only bin/, rules/, README and LICENSE. Hook, installer and skill body quality were not read.
- Where an angle authored an idea, that angle is counted in votesFor.
- /opm:status and /opm:dashboard are built as plugin slash commands, not skills. This assumes command descriptions do not count toward the always-on budget the way skill descriptions do; to verify against Claude Code.
- The installer writes a new version stamp file (.claude/rules/opm/.opm-version with per-file hashes) so doctor can tell when rules are out of date. The fact sheet does not describe any existing stamp.
- doctor finds the installed plugin directory on disk to replay hook scripts with synthetic payloads, so the npm package files list does not need to include hooks/.
- The tested Claude Code version range is declared in package.json or README and read by doctor. The way doctor reads the local Claude Code version (for example `claude --version`) is assumed.
- The 'about 4KB' SKILL.md target and the CI ceiling value are set from the first linter run, not chosen in advance.
- The chars-per-token constant (for example about 4 for English markdown) is an estimate and is published as one.
- Always-on cost is assumed to be skill and agent descriptions, plus rules/common, plus SessionStart output; the linter documents exactly what it counts.
- The SessionStart open-ledger line counts as open any ledger whose plan has a task with no 'complete' line; the last-modified time is shown but stale ledgers are not hidden.
- The dashboard reads the current repo plus paths listed in an optional local config (for example ~/.opm/projects.json); it does not discover or watch repos.
- Usage events store a salted hash of the project, never a path or prompt text, and report output contains only counts.
- The secret-leak check on edit warns and does not block, using a small built-in pattern list.
- The destructive-command guard limits rm -rf blocking to paths outside the repo or root-like targets; the exact rule set is decided while building it.
- The trigger fixture holds 30 cases for the routing table, and the eval harness extends it to 30-40 once the `claude -p` spike shows whether skills trigger in that mode.
- Hook messages appear in the Claude Code transcript through the existing hook output channels; how each payload is rendered depends on Claude Code.
- Phases map to releases 0.7.0, 0.8.0 and 0.9.0 as in the verdict plan, with Phase 4 having no version until it has evidence.
- All four angles returned proposals and every angle was rebutted; no missing or silent angles.

## Why these choices

One or two sentences per angle: its position and the argument that changed the result. Market claims marked unverified were not checked online.

- **Product**: Put adoption and visibility first: CI, a measured token number, a first-run path and /opm:status. The skeptic and engineering showed that /opm:start would add a 17th always-on description, so its job moved into doctor plus the routing table.
- **Engineering**: Make reliability and per-run cost the priority: CI matrix, token linter, doctor, a louder Stop hook, and splitting large skills into a core plus on-demand references. The skeptic and market rejected its Stop-hook cache because a stale cache could report a false green, so the cache was deferred.
- **Skeptic**: Stop adding surface and prove the claims first: measure tokens, harden existing hooks before adding new ones, and trim overlap. Its high-severity attacks forced the positioning work and the new guard hook to wait for measured numbers and hardened hooks, and helped push explainer-video out of core.
- **Market**: Win on credibility against superpowers: measured cost, marketplace listing and safety hooks as a differentiator. Its web search raised the possibility that `claude -p` does not trigger skills (unverified), which made the eval harness start with a spike; its first-run rules-install hook was cut on consent grounds.
