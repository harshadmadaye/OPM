# opm brew

Date: 2026-10-05 (revision 1 of 2026-10-02)
Brief: Give a prioritized improvements list and new feature updates for this current plugin project: OPM, an opinionated engineering-workflow plugin for Claude Code (v0.6.1) used by developers in the terminal and IDE. It ships skills, reviewer agents, safety hooks, rules and an npx installer. Improve reliability, adoption, onboarding, token cost and day-to-day developer usefulness; propose what to fix, what to add next, and what to cut.
Source: brew-idea run wf_8a106824-7a3

## Vision

OPM is a low-token, test-first, evidence-before-done workflow plugin for solo and small-team developers using Claude Code in the terminal and VS Code. It pairs measured token costs with guardrails that run on every call, and it uses in-process mods for status and safety at no model cost.

OPM 0.7-0.9: a measured, low-token, test-first Claude Code workflow where status, safety and cost checks run as code instead of model turns, and every release is gated by CI.

Goals:
- Every release is gated by CI on macOS, Linux and Windows x Node 18/20/22, with a version/manifest gate, npm pack check, a token-budget ceiling and `claude plugin validate --strict` / `claude plugin test`.
- The token-cost claim is backed by numbers: the static linter holds always-on cost in CI, core SKILL.md files drop to about 4KB, and an opt-in local meter records measured per-request usage.
- A new user goes from `npx opm-core@latest` to a healthy install confirmed by `doctor`, and small tasks go straight to tdd-workflow instead of the full spec, plan and subagent pipeline.
- Status, resume and destructive-command safety need no Claude turn and print plain text in the VS Code panel; settings hooks remain the fallback on Claude Code older than v2.1.287.

Not doing:
- Remove the story-video alias in 0.7.0 (cut: no alias is designed or kept)
- verification-loop as a separate skill (merge into verification-before-completion with quick and full-gate modes) (cut)
- push-via-api.sh in the shipped package (cut)
- Static HTML /opm:dashboard and a mod-pane dashboard (cut; `/opm:status --all` covers the need in text)
- /opm:start skill and bundled sample repo (cut; doctor, the installer next-step line and the routing table cover first run)
- Collapse the front-door skills into one router skill (cut until eval data shows real collisions)
- No panes, bands, status lines or spinner restyles: the developer uses the VS Code chat panel, which does not draw them
- No telemetry and no network calls from hooks, mods or the CLI; the meter stays local and off by default
- No changes to the user's permission mode
- No hot-path hook migration unless the dedupe spike finds a supported way to stop settings hooks firing alongside the mod
- No competitor figures in README or listings; only OPM's own measured numbers
- No new stacks (Go, Rust, Java) in this plan

Success looks like: The 0.8.0 release PR passes CI on all three operating systems with the token-budget check under its ceiling, and in the VS Code chat panel `/opm:status` prints the open ledger task in about 5 lines without starting a Claude turn.

## Design

### Who uses it

**Harshad, the author running several OPM projects in VS Code**: Knowing where each project's plan stands, and resuming without spending tokens or re-dispatching tasks that are already done, all inside the VS Code chat panel.
Flow: Opens a Claude Code session in project A in VS Code → The SessionStart hook adds one line: open ledger docs/plans/...progress.md, task 4 of 9 → Types /opm:status; the mod prints 5 lines (plan, task, last ruling, done/total) with no Claude turn → Types /opm:status --all to see projects B and C from per-session $.store entries → Asks Claude to resume; executing-plans reads the ledger and continues at task 4 → Claude tries `git push --force origin main`; the guard holds it with $.ui.ask, he picks cancel

**A new adopter, a solo TypeScript or Python developer**: Installing OPM, confirming it works, and getting a useful first result without reading the whole README or paying for the full pipeline on a 10-line fix.
Flow: Finds OPM in a plugin marketplace listing or the README → Runs `npx opm-core@latest`, picks rules in the checkbox picker → The installer ends with one line: run `npx opm-core doctor` → doctor reports Node, hook registration, rule freshness, tools and Claude Code version; one warning says ruff is missing, with the fix → Asks Claude for a small bug fix; the using-opm routing table sends it straight to tdd-workflow → The Stop hook skips tsc because no .ts files changed and runs ruff on the edited Python files

**The maintainer cutting a release**: Shipping fast without breaking manifests, Windows hooks, the always-on token budget or mod contracts when the Claude Code CLI changes.
Flow: Opens a PR that adds a new section to executing-plans → CI runs node:test on the OS x Node matrix, the version/changelog/manifest gate, npm pack --dry-run, validate --strict and plugin test → The token linter fails: executing-plans exceeds its soft cap → Moves the detail into skills/executing-plans/references/ and re-pushes; CI goes green → Later, the scheduled job against the latest claude CLI fails validate, which signals mod API drift before users hit it → Bumps the declared tested range after fixing it, and doctor shows the new range

#### npx opm-core@latest (installer) (command)

Install the plugin and copy the chosen rules per repo, with the optional explainer-video plugin offered separately, then point to doctor. Delivers: Installer, rules, agents, compound-learnings, milestone-planning, jump-start, dev-server.sh and the existing settings hooks; `npx opm-core doctor`: Node version, hook registration, rule freshness against the plugin version, tool presence, synthetic-payload hook replay and the Claude Code version against the tested range; the installer ends with one next-step line; Spin explainer-video out into an optional second plugin in the same marketplace, with lazy pinned tool install and disclosure of cloud TTS.

```
header: OPM version and target repo path
picker: checkbox list of rule sets (common, typescript, react, python, dart)

optional line: explainer-video is now a separate plugin, plus the install command and a note that its TTS sends text to a cloud service
footer: one next-step line, `npx opm-core doctor`
```

States: Empty: no repo detected, so it offers --plugin-only; loading: one line per step; error: a friendly one-line cause and fix, full detail only with --verbose, non-zero exit.

#### npx opm-core doctor (command)

Check install health from outside a session and on any Claude Code version; this is the support and onboarding tool. Delivers: `npx opm-core doctor`: Node version, hook registration, rule freshness against the plugin version, tool presence, synthetic-payload hook replay and the Claude Code version against the tested range; the installer ends with one next-step line; Declared tested Claude Code range, plus a scheduled CI job running `claude plugin validate --strict` and `claude plugin test` against the latest CLI.

```
header: OPM plugin version, Node version, Claude Code version vs tested range
checks list: one row per check, pass / warn / fail with a one-line detail
mods row: mod features on (>= v2.1.287) or settings-hook fallback only
fix list: the exact command to run for each warn or fail
footer: summary count and exit code
```

States: Empty: no plugin found, so a single fail row says how to install; loading: rows print as each check finishes; error: a check that crashes reports as fail with its reason, never a stack trace.

#### In-session OPM context and hook feedback (other)

What the model and user see during a session: the routing table and resume line at start, skills loaded on demand, and visible Stop hook results. Delivers: Routing table in using-opm with a size ladder (a small-task path straight to tdd-workflow) plus a static 30-prompt trigger fixture; Split large skills into a short SKILL.md plus references/ files; Make brew-idea user-invoked only; Stack pattern skills: dedupe against the rules so each piece of guidance has one source; Stop hook: skip when no files of that language changed, and warn visibly on a missing tool or when the 90s limit nears; /opm:status as a mod command (mod-based), an `npx opm-core status` fallback, and a one-line open-ledger resume note in the existing SessionStart hook; Migrate the hot-path hooks (block-no-verify, config-protection, post-edit accumulator) to in-process mod hooks, gated on a dedupe spike.

```
session start: the using-opm text with a routing table (task size -> skill)
session start: at most one resume line when a ledger is open
on demand: short SKILL.md, with references/ files read only when a step needs them
Stop: one line per language checked or skipped, plus warnings for a missing tool or nearing the 90s timeout
```

States: Empty: no ledger, so no resume line, and no changed files, so Stop prints nothing; loading: Stop runs within 90s; error: a missing tsc/ruff/dart or a timeout shows a visible warning instead of passing silently.

#### /opm:status, /opm:status --all and npx opm-core status (command)

Show the open plan and task for this repo, or across every project on the machine, with no Claude turn; the npx form is the fallback before v2.1.287. Delivers: /opm:status as a mod command (mod-based), an `npx opm-core status` fallback, and a one-line open-ledger resume note in the existing SessionStart hook; Multi-project view via `/opm:status --all` reading per-session entries from $.store (mod-based), replacing /opm:dashboard; Workflow engine: executing-plans with a fresh subagent per task, a reviewer gate and an on-disk ledger.

```
line 1: plan file and ledger path
line 2: tasks done / total and the current task title
line 3: the last ruling or fix round from the ledger
line 4: last-updated time and branch
line 5: a hint, 'ask Claude to resume plan'
--all variant: one row per project (repo, plan, done/total, last seen), at most about 30 lines
```

States: Empty: 'no open ledger in this repo'; loading: none (code answers immediately, even while Claude works); error: an unreadable or malformed ledger prints one line naming the file, and stale $.store entries are marked stale.

#### /opm:report (opt-in token meter) (command)

Turn measured per-request usage and skill invocations into a short copy-paste summary that backs the cost claim and the cut list. Delivers: Opt-in local usage and token meter mod (mod-based): turn.complete usage and skill.prompt skill names in a capped $.store key, with `/opm:report` as a copy-paste summary.

```
status line: meter on or off, and how to toggle it
totals: requests, input, output, cache read and cache write tokens over the window
per-skill table: skill, times fired, median tokens per request
footer: the store size used vs its cap, and 'local only, nothing sent'
```

States: Empty: meter off, so it shows the enable command; on but no data yet, so it says no turns recorded; error: a corrupt store key is reset with a one-line notice.

#### Destructive-command hold (other)

Hold rm -rf, a force-push to main and reset --hard before they run, and let the user proceed or cancel; deny with a reason where asking is impossible. Delivers: Destructive-command guard as a tool.call mod (mod-based): hold rm -rf, force-push to main and reset --hard with $.ui.ask, fail closed through .catch; Hook threat model doc and tests for known evasion variants (git commit -n, HUSKY=0, core.hooksPath).

```
title: 'OPM held a destructive command'
body: the exact command and what it would affect (paths, branch, commits)
actions: Proceed / Cancel via $.ui.ask
fallback text: in claude -p or where the ask cannot render, a deny reason Claude reads, with a pointer to the threat model
```

States: Empty: not shown for safe commands; loading: the call is held while the user decides, which does not count against the 10s limit; error: any exception in the guard denies the call (fail closed) with a one-line reason.

#### GitHub Actions CI checks (page)

Deterministic release gate on every PR, a scheduled drift check against the latest claude CLI, and a manual or nightly trigger eval. Delivers: GitHub Actions CI: node:test on macOS/Linux/Windows x Node 18/20/22, a version/changelog/manifest gate, npm pack --dry-run and `claude plugin validate --strict`; Static token-budget linter (bytes/4 estimate) with an always-on CI ceiling and per-skill soft caps; Declared tested Claude Code range, plus a scheduled CI job running `claude plugin validate --strict` and `claude plugin test` against the latest CLI; Skill-trigger eval harness (headless, manual or nightly) after a design spike.

```
PR checks: test matrix (3 OS x 3 Node), manifest gate, pack dry-run, validate --strict, plugin test, token budget
token budget log: always-on estimate vs ceiling, then per-skill size vs soft cap
scheduled job: validate and plugin test against latest CLI, red on drift
manual workflow: skill-trigger eval run against the 30-prompt fixture with a per-prompt hit/miss table
```

States: Empty: not applicable; loading: jobs queued or running; error: a failing job names the file and budget or check that broke, and the eval workflow is skipped when no API secret is configured.

### Stack

| Choice | Reason |
|---|---|
| Node >= 18, CommonJS scripts, zero runtime dependencies (unchanged) | Keeps the install small and dependency-free, and keeps hooks safe to run on every call. |
| node:test for unit tests, the token linter and the static trigger fixture (unchanged runner, new tests) | Deterministic, needs no network or session, and already runs the 15 existing test files. |
| Plain JavaScript ES module for the mod's register.js (new) | Mods load as ES modules; plain JS avoids a TypeScript build step and keeps zero dependencies. |
| `claude plugin validate --strict` and `claude plugin test` with the claude-code/testing kit (new, CI only) | The official way to check mod events and APIs and to test mods with stubs and a mock clock, with no sign-in or network. |
| Pinned claude CLI as a dev-only CI dependency, plus a scheduled job on the latest CLI (new) | Pinning keeps PR checks stable, and the latest-CLI job catches mod API drift early. |
| GitHub Actions (new) | Free for a public repo, gives the macOS, Linux and Windows matrix, and fits the existing .github directory. |
| $.store for the status cache and opt-in meter (new, mod-based) | Shared by every session on the machine and needs no network; the on-disk ledger stays the source of truth. |
| Settings command hooks kept beside the mod in one hooks.json | Fallback below v2.1.287 and the only place the 90s Stop typecheck can run, since a mod hook is capped at 10s. |
| Sibling references/ markdown files rather than skill.prompt injection | Simpler, works on every Claude Code version, and the linter can measure it. |
| headless browser, ffmpeg and edge-tts move to the explainer-video plugin (changed) | Removes external tools and the cloud TTS call from core, which keeps the no-network promise. |

## Plan

### Phase 1: (0.7.0): Safety net and measurement

Goal: Gate every release on deterministic checks and turn the token claim into a CI number. Everything after this phase depends on it.

Features:
- GitHub Actions CI: node:test on macOS/Linux/Windows x Node 18/20/22, a version/changelog/manifest gate, npm pack --dry-run and `claude plugin validate --strict`
- Remove the story-video alias in 0.7.0
- Static token-budget linter (bytes/4 estimate) with an always-on CI ceiling and per-skill soft caps
- push-via-api.sh in the shipped package

Risks:
- Installing a pinned claude CLI in CI adds a dev-only dependency, and the validate output format may change
- The Windows run may expose real breakage in the shell helpers (dev-server.sh, install-rules.sh) that has to be fixed or explicitly scoped out
- bytes/4 is an estimate, so the ceiling needs headroom to avoid flaky failures

### Phase 2: (0.7.x): Trim and steady the core

Goal: Cut per-run tokens, make routing obvious, and make install and hook failures visible. All of this uses settings hooks only and works on every Claude Code version.

Features:
- Routing table in using-opm with a size ladder (a small-task path straight to tdd-workflow) plus a static 30-prompt trigger fixture
- Split large skills into a short SKILL.md plus references/ files
- verification-loop as a separate skill (merge into verification-before-completion with quick and full-gate modes)
- `npx opm-core doctor`: Node version, hook registration, rule freshness against the plugin version, tool presence, synthetic-payload hook replay and the Claude Code version against the tested range; the installer ends with one next-step line
- Stop hook: skip when no files of that language changed, and warn visibly on a missing tool or when the 90s limit nears
- Hook threat model doc and tests for known evasion variants (git commit -n, HUSKY=0, core.hooksPath)
- Make brew-idea user-invoked only
- Spin explainer-video out into an optional second plugin in the same marketplace, with lazy pinned tool install and disclosure of cloud TTS
- Stack pattern skills: dedupe against the rules so each piece of guidance has one source

Risks:
- Splitting skills can change model behaviour if the core loop loses context it needs; check with the trigger fixture and a manual run
- Moving explainer-video out breaks existing users' commands, so it needs a migration note and a release with a pointer
- The routing table makes using-opm larger, so its growth must fit within the linter ceiling

### Phase 3: (0.8.0): First mod (register.js next to the existing hooks.json, requires v2.1.287 or later, settings hooks kept as the fallback)

Goal: Add status, safety and measured tokens with no model turns. Each feature prints text that works in the VS Code panel, and every mod ships with `claude plugin test` coverage in CI.

Features:
- /opm:status as a mod command (mod-based), an `npx opm-core status` fallback, and a one-line open-ledger resume note in the existing SessionStart hook
- Destructive-command guard as a tool.call mod (mod-based): hold rm -rf, force-push to main and reset --hard with $.ui.ask, fail closed through .catch
- Opt-in local usage and token meter mod (mod-based): turn.complete usage and skill.prompt skill names in a capped $.store key, with `/opm:report` as a copy-paste summary
- Declared tested Claude Code range, plus a scheduled CI job running `claude plugin validate --strict` and `claude plugin test` against the latest CLI

Risks:
- The mod API is new and may change; pin the tested version and let the scheduled job catch drift
- Mods are unsandboxed in-process code, a trust cost: keep the surface small, make no network calls, and publish the `claude plugin validate --json` list of events and APIs in the README
- $.ui.ask may not render in the VS Code chat panel or claude -p, so the guard must deny with a clear reason there
- The 4 MiB $.store is shared by every session on the machine, so the meter must prune and cap its key
- Command output that Claude reads still costs a few context tokens, so keep it to a few lines

### Phase 4: (0.9.x): Evidence-driven growth

Goal: Use measured data to decide merges, migration, positioning and the multi-project view.

Features:
- Skill-trigger eval harness (headless, manual or nightly) after a design spike
- Migrate the hot-path hooks (block-no-verify, config-protection, post-edit accumulator) to in-process mod hooks, gated on a dedupe spike
- Rewrite README and why-opm.md positioning around measured cost and guardrails
- Submit OPM to the official and community plugin marketplaces
- Multi-project view via `/opm:status --all` reading per-session entries from $.store (mod-based), replacing /opm:dashboard

Risks:
- claude -p may not trigger skills, which would leave the eval harness with no signal
- With no dedupe path, hooks would fire twice, so the migration may have to be abandoned
- The measured cost numbers may be unfavourable, which would change the positioning story
- The multi-project view may serve only the author

## Assumptions

- Measured locally: skill files total 152,498 bytes, executing-plans is 20,151 bytes, and .github holds only issue and PR templates. hooks.json currently has command hooks only.
- A mod's 10s hook limit includes awaited $.process.run time, so the Stop typecheck must stay a settings hook with its 90s timeout.
- A mod in a plugin cannot stop that plugin's own settings hooks from also firing, so migrating existing hooks risks double-firing and needs a spike.
- Commands registered with $.command.register do not add a description to the always-on skill listing; their output costs only the few tokens Claude reads.
- The claude CLI can be installed in GitHub Actions and run `plugin validate` and `plugin test` without sign-in, as the mods docs state.
- bytes/4 is a good enough token estimate for a CI ceiling with headroom.
- $.ui.ask may not render in the VS Code chat panel or under claude -p, so a fail-closed deny is the safe default there.
- edge-tts sends narration text to a Microsoft cloud endpoint, which conflicts with the no-network promise for core.
- A plugin marketplace can list a second, optional plugin from the same repo.
- The on-disk ledger stays the source of truth, with $.store holding only a cache keyed per session ({repo, plan, task i/n, lastVerdict, updatedAt}) plus one capped, opt-in usage key.
- The skeptic's comments in its rebuttals stand for its votes, and developer feedback, which is not an angle, counts for no angle votes.
- The developer uses the VS Code extension chat panel, so every mod surface outputs text through command output or $.ui.log and never relies on panes, bands or status lines.
- register.js is loaded as an ES module even though package.json has no "type": "module"; if not, a hooks/package.json with type module or a .mjs file is needed. To be confirmed in a spike.
- `claude plugin test` runs *.test.ts files without a separate build step, using the pinned CLI in CI.
- The shared ledger module is CommonJS, imported by the ESM mod through Node interop; its location (for example lib/ledger.js) is not decided.
- The $.store key names (for example opm.sessions and opm.meter), the 14-day pruning age and a cap of about 256 KiB for the meter key are proposals.
- The meter is toggled through `/opm:report --enable` and `--disable`; the verdict says only that it is opt-in.
- Protected branches for the force-push guard are main and master; the exact rm -rf patterns held (for example paths outside the repo, or any recursive force delete) are not decided.
- Where $.ui.ask cannot render, it either throws or reports that it is unsupported, so the .catch handler can deny with a reason.
- The Stop hook's 'nearing the limit' warning fires at about 75s of the 90s timeout.
- The installer writes a version stamp file into <repo>/.claude/rules/opm/ so doctor can check rule freshness; this file does not exist today.
- doctor exits 0 when all checks pass, 1 on any fail, and treats warnings as exit 0.
- The token budget's starting values are an always-on ceiling of about 2,600 estimated tokens (2,300 plus headroom) and a soft cap of about 1,000 tokens (about 4KB) per core SKILL.md.
- The size ladder thresholds in the routing table (for example one file or about 10 lines goes to tdd-workflow, up to 3 tasks uses writing-plans inline mode, multi-week work goes to milestone-planning) are proposals.
- The 30-prompt fixture is checked statically against the routing table text; only the eval harness checks real model triggering.
- The eval harness needs an API key secret in CI, runs only manually or nightly, and is skipped when the secret is absent.
- The initial declared tested range for mod features is v2.1.287 to v2.1.289; the lowest Claude Code version the settings-hook fallback supports is unknown.
- The Windows CI run may force dev-server.sh and install-rules.sh to be ported or explicitly scoped out as Unix-only.
- The threat model lives at docs/threat-model.md and is linked from the README and the guard's deny text.
- The explainer-video plugin's name (for example opm-explainer-video) and its migration pointer from core are not decided.
- The requirements of the official and community marketplaces are unverified and are checked before submission.
- The SessionStart resume line only looks for docs/plans/*.progress.md in the current repo and prints at most one line.
- No supported way to stop plugin settings hooks from firing alongside mod hooks is known yet, so by default the hot-path hooks stay as settings hooks.
- All four angles returned proposals and every angle was rebutted; no missing or silent angles.
- Mods facts come from the official Claude Code docs (code.claude.com/docs/en/plugins/mods/*) read on 2026-10-05; the debate rounds predate them, only the judge and designer saw them.

## Why these choices

One or two sentences per angle: its position and the argument that changed the result. Market claims marked unverified were not checked online.

- **Product**: Put adoption and visibility first: CI, a measured token number, a first-run path and /opm:status. The skeptic and engineering showed that /opm:start would add a 17th always-on description, so its job moved into doctor plus the routing table.
- **Engineering**: Make reliability and per-run cost the priority: CI matrix, token linter, doctor, a louder Stop hook, and splitting large skills into a core plus on-demand references. The skeptic and market rejected its Stop-hook cache because a stale cache could report a false green, so the cache was deferred.
- **Skeptic**: Stop adding surface and prove the claims first: measure tokens, harden existing hooks before adding new ones, and trim overlap. Its high-severity attacks forced the positioning work and the new guard hook to wait for measured numbers and hardened hooks, and helped push explainer-video out of core.
- **Market**: Win on credibility against superpowers: measured cost, marketplace listing and safety hooks as a differentiator. Its web search raised the possibility that `claude -p` does not trigger skills (unverified), which made the eval harness start with a spike; its first-run rules-install hook was cut on consent grounds.
- **Revision 1 (developer feedback)**: The judge and designer reran with facts from the Claude Code mods docs. Status, the usage and token meter, the destructive-command guard and the multi-project view became mod-based, with settings hooks and an npx fallback kept for VS Code and Claude Code older than v2.1.287. The dashboard and mod UI panes were cut because nothing draws in the VS Code chat panel.
