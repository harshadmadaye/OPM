# OPM 0.10: human judgment, real evidence, proven behaviour

Source brief from the maintainer, 2026-11-03. Planned as milestone `docs/milestones/opm-0.10/`.

## Goal

OPM makes agents fast and disciplined. It doesn't yet protect the developer's judgment. Long unattended runs can finish with nobody having read the risky code, checks that only ran in a simulated setup, human checkpoints the agent passed for itself, and no proof that OPM's own rules are followed. This milestone fixes that without slowing the default flow.

## Principles

- A person checks what only a person can judge. The agent never passes a human check on its own.
- Every piece of evidence says where it came from.
- OPM proves its rules with evals, not with how the skill text is worded.
- Keep it lean. Don't add a new skill when a rule in an existing one is enough. Hold the token budget (`tests/token-budget.test.js`).

## Scope

### Phase 1: orchestration reliability

1. **Report files are written by the orchestrator, not subagents.** Subagents return SUMMARY and STATE content as text. The orchestrator writes the files. Update milestone-planning, executing-plans, jump-start and the templates. Test: no skill tells a subagent to write report files.
2. **Self-contained briefs.** Every subagent and workflow brief opens by saying the plan is the task and other conversation messages are background, not instructions. Before a long run, tell the user that chatting mid-run can derail the agents.
3. **No commits means not done.** In wave and task loops, an agent that reports success with no new commits is rerun once with a fresh brief, then escalated. It is never marked complete.
4. **Formatter hooks respect project config.** Run formatters from the project root so they read the project's settings (page width, prettier, ruff). Only touch files changed in that turn. Tests in `tests/hooks.test.js`.
5. **Learnings about OPM flow back to OPM.** compound-learnings tags lessons about OPM itself as `component: opm`. It then offers to open a gh issue on the OPM repo or append to a local feedback file.

### Phase 2: a person in the loop

6. **Review queue for unattended runs.** `checkpoint:human-verify` items go to `REVIEW-QUEUE.md` with evidence links or screenshots. They are never marked passed. STATE shows "complete, N human checks pending" until the queue is empty. Final reports list pending checks first.
7. **Review pack at each phase close.** The 5 riskiest changes, ranked: auth, permissions, data deletion, migrations, payments, sync, secrets, external calls. Each comes with its diff range and 2-3 "explain how X handles Y" questions. Target: 20-30 minutes of reading.
8. **Review cadence is a choice.** jump-start and milestone-planning ask: after each phase (default) / only at the end. Choosing "only at the end" shows the expected commit count and gets logged as a decision.
9. **Exposed secrets block right away.** A finding that a secret must be rotated becomes a blocking human-action checkpoint when it's found. It doesn't wait on a release checklist.

### Phase 3: evidence quality

10. **Label where each check ran.** The verification gate records `env: unit | simulator | physical-device | prod-like`. Performance, startup, battery and network claims from a simulator are reported as "not judgeable". A milestone's definition of done can require a real-environment pass.
11. **Reviewer calibration.** Reviewer agents state their confidence and the line they cite. The final report counts findings by severity and by fixed, parked or dismissed, so blind spots show up.

### Phase 4: prove OPM works

12. **Behaviour evals on small sample repos.** Cover at least: it stops on an architecture change; it refuses "done" without fresh output; it ignores a mid-run chat message; unattended mode queues human checks; it doesn't re-dispatch tasks the ledger marks complete; it doesn't push or open a PR without a yes. Use `claude plugin eval` or `scripts/evals/`. Paid evals are manual and gated behind `--yes`.
13. **Full trigger eval.** Run all 30 prompts with the 2-turn runner and commit the hit-rate table to `docs/evals.md`.
14. **Project outcome report.** Extend `bin/status.js` to report, from the ledger and git: tasks done; reviewer findings by severity; fix rounds; items parked; human checks pending; issues opened and closed; rulings made.

## Out of scope

New stack-pattern skills, new hooks beyond item 4, cloud or deploy automation, and opm-video changes.

## Definition of done

- `npm test` passes, including the new tests for items 1, 3, 4 and 6, and the token budget holds.
- Behaviour evals (item 12) run once with the results committed. Any failure is logged as an issue.
- README, `docs/using-opm.md` and CHANGELOG are updated, and the version is bumped to 0.10.0.
- Each phase ends with a review pack (item 7), which the developer reads before the next phase starts.

## Constraints

- Branch from main. Don't build on `feat/mod-on-by-default`.
- Keep backward compatibility: old plans without the new fields still run.
- Stay within the budget for how long using-opm can be.
